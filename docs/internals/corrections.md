# Corrections

Corrections put a library right from MusicBrainz, starting from evidence gathered beside the files. What is built so far is that evidence: the sidecars a scan keeps with the audio, the CD layouts read from them, MusicBrainz's replies about those discs, the album and edition proposals worked out from them, and the answers that say yes or no to one, keep two albums apart, or undo another answer. Pure layout and reply reading, proposing, values and previewing live in `crates/ritornel-domain/src/{layout,reply,propose,values}.rs`; storage, derivation and answers in `crates/ritornel-engine/src/{evidence_store,lookup_store,proposal_store,answer_store}.rs`; the scan's part in `crates/ritornel-engine/src/{walk,scan}.rs`; the fetching in `crates/ritornel-musicbrainz`; the calls in `apps/server/src/dispatch/corrections.rs`; and the commands in `apps/ritornelctl/src/corrections.rs`.

See [`docs/internals/identity.md`](identity.md) for the scan these steps ride on, [`docs/internals/schema.md`](schema.md) for durable and rebuildable tables, and [`docs/internals/plugins.md`](plugins.md) for the `Catalogue` trait.

## Disc layouts

A layout is where each track of a CD starts and where its audio ends, in sectors of 1/75 second. It gives the disc's MusicBrainz disc ID, which an exact lookup asks about. Rips carry their layout in what the ripper left beside the audio, and a scan keeps those files so the layout can be worked out again at any time without reading the audio.

### Sidecars

The walk (`walk.rs`) lists every file that may be a sidecar: `.cue`, `.log` and `.accurip` files, and `.txt` and `.nfo` files, each at most `SIDECAR_MAX_BYTES` (1 MiB). The scan keeps those that sit near audio: in a folder of audio, in a folder inside one (such as `Misc/` or `Support/`), or in the folder above one. A `.txt` or `.nfo` file is kept only if it reads as a rip log (`layout::keeps`): it names Exact Audio Copy, X Lossless Decoder or cdda2wav.

Sidecars are read after the audio and before the resolver, in a phase of the scan job of their own (`Phase::Sidecars`): each step reads files whose sizes, as the walk found them, come to at most `SIDECAR_BATCH_BYTES` (8 MiB), kept or not, and never more than one byte past the cap from any file, and each batch that changes anything is recorded in one library write (`SIDECARS_METHOD`, `scan.sidecars`):

- **`sidecar`** is one file by `(source_instance_id, rel_path)`, with its size and modification time so an unchanged file is not read again, and `missing_since_ms` set when a scan of a reachable root no longer finds it, or finds it no longer a sidecar, such as a text file that no longer reads as a rip log. A file in a folder the walk could not read is left as it was, and a folder of audio the walk could not read still counts as one, so the log above it is kept.
- **`sidecar_revision`** holds the bytes as read, deduplicated per sidecar by their BLAKE3 hash, and is immutable (`sidecar_revision_no_update`, `sidecar_revision_no_delete`, and `sidecar_revision_no_replace` against an `INSERT OR REPLACE`). A file that changes and changes back takes its earlier revision again.

Bytes are stored as found. Rip logs come as UTF-16 with a byte order mark, as UTF-8, and as Windows-1252, and `layout::decode` reads each.

### Reading a layout

`layout::layouts` (`LAYOUT_VERSION = 1`) is a pure function from each folder's audio files and the sidecars near it to that folder's layouts. A folder's own sidecars count, and those in a folder inside it that holds no audio. The sidecars of a folder above it that holds no audio count only for a layout that fits the folder's files exactly, as one log of a two-disc set does. Each layout is found in one or more ways (`Method`):

| Method | From | Checked by |
|---|---|---|
| `log` | A drive's table of sectors in a rip log, as EAC and XLD print it, or the start sectors cdda2wav prints | Nothing more: the drive read the disc. An end sector is the track's last, and on an enhanced CD the audio ends where the 11,400-sector gap before the data session begins |
| `cue` | A CUE sheet, with each `INDEX 01` taken from its `FILE` and the exact length of each file it names. A declared `PREGAP` or `POSTGAP` is added. A data track after the audio ends the audio where its `INDEX 00` says | The CDDB ID the sheet itself prints in `REM DISCID`, if any, counting a data track. A sheet that disagrees gives a **provisional** layout |
| `renamed_cue` | A CUE sheet whose files were renamed since: its `FILE` names matched to the folder's files by track number | The CDDB ID the sheet prints, or with none printed, every file's title ending the name the sheet gave it |
| `accuraterip` | The files' lengths in order | An AccurateRip disc ID printed in an `.accurip` report, with its pregap |
| `cddb` | The files' lengths in order | A CDDB ID any CUE sheet of the folder prints, when a renamed sheet was the only other way found |

A file's length in sectors comes from the stored `duration_ms` of its audio, for lossless stereo at 44.1 kHz only (`layout::sectors`). A number in a sidecar that no CD can hold, past 32 bits with the lead-in, is read as nothing. The stored length is cut to the millisecond, and a sector is 13⅓ ms, so the count is exact for a file that is a whole number of sectors; most files that are not are seen not to be. The disc ID is computed as MusicBrainz's "Disc ID Calculation" defines it: SHA-1 over the first and last track numbers, the lead-out and 99 offset slots, each offset with the 150-sector lead-in, in MusicBrainz's base64 alphabet.

Two layouts of one folder's files that disagree are both kept, such as a drive's log and the files of a rip that stripped its gaps. Each layout places a file at each position when every position has exactly one file of that length and, where the file has one, that track number. A folder of one file the length of a disc of several tracks is a whole-disc image; a disc of one track that file fills is that track.

### Derivation

The layouts are derived (`LAYOUTS_METHOD`, `corrections.layouts`) as the last step of a scan job when they are due: a write since the last derivation said so, or they were derived by another `LAYOUT_VERSION` than the build's (`library_setting` key `corrections.layout_version`). A write of sidecars, and a write of files in a library that has sidecars, says so in its own transaction (`corrections.layouts_pending`), so a scan that stops before it derives leaves them due for the next. Derivation reads only stored rows: the live sidecars' current revisions, the live files' audio assets, and their own `track_number` and `title` tags. It writes the difference from what is stored to the rebuildable tables, and clears the mark that they are due even when there is none, so a derivation always takes a revision:

- **`evidence_disc`** is one layout of one folder, by `(source_instance_id, folder, disc_id)`: the track offsets, the lead-out, each way it was found with the `sidecar_revision` it was read from (`found_json`), whether it is provisional, whether one file holds it, and the `layout_version` it was derived by.
- **`evidence_disc_item`** is the source item at each position, or at position 0 for a whole-disc image.

### Queries

`corrections.discs` (query, `full` session) lists every layout with its root, folder, disc ID, track count, length, methods and whether its files were matched, with counts of folders holding audio and of those with a layout that is not provisional. With `folder` it lists one folder's layouts with the file at each position. `ritornelctl corrections discs [<folder>]` prints it.

## MusicBrainz lookups

MusicBrainz is asked about a disc by its disc ID, and each reply is kept as it came. Nothing it says reaches what the app shows: a reply only adds evidence.

### The switch

A library is not asked about until its `lookups` setting is on, and with it on, only an album or a folder that `corrections.lookup` names is asked about: nothing is looked up by itself, after a scan or otherwise. `library.settings` (query) reports it as a `Setting`, with `setBy` `default` until a call sets it, and `library.setSettings` (command) changes it, taking an idempotency key and the settings to change (both `full` sessions, and forwarded to the hub on a satellite, as other library calls are). It is kept in `library_setting` under `corrections.lookups`; absent is off. `ritornelctl corrections musicbrainz on | off` sets it. What leaves the machine is the disc ID and the fixed inclusions: never a path, a file, or anything about who runs it. The User-Agent is `Ritornel/<version> ( https://ritornel.app )` (`USER_AGENT` in `ritornel-musicbrainz`).

### Asking about one album

`corrections.lookup` (command, `full` session) names one album, a release by its ID or a folder by its path under its root (with `root` when more than one root has that path), and asks about the disc IDs of the layouts in the folders it covers (`discs_of`). It is refused as `unavailable` with the reason `lookups_off` while the switch is off, `no_catalogue` on a server built without the `musicbrainz` feature, as `invalid` when the folder is in more than one root and none is named, and as `not_found` with `no_discs` for an album with no layout. The server advertises the `corrections.lookup` capability when it has a catalogue.

- **Asked once.** A disc that has a current reply to the same request is not asked again unless the call says `again`. A "no such disc" (404) is a reply and counts. A request is the catalogue, the kind of question, its key and what it asked to be included (`DISC_INCLUDES`: `artist-credits+release-groups+recordings`, with CD stubs off), so a reader that needs more asks a new request.
- **Asked, then kept.** The catalogue is asked before the library is written. The replies and the receipt are then kept in one library write (`corrections.lookup`), so the same idempotency key is answered from the receipt and asks nothing. One lookup runs at a time, from the check of its receipt to its commit, so no two ask the same thing at once, and the switch is read again before each request, so a lookup turned off on its way stops there.
- **Only a reply is kept.** A reply is JSON in UTF-8 that reads as an answer about the disc asked: its releases, or MusicBrainz's own "no such disc". Anything else (a timeout, no network, 503 or 429, any other refusal, a redirect, a page from something in the way) is that disc's `failed` outcome with a one-line reason, nothing is kept for it, and the reply it had stays current.
- **Paced.** `ritornel-musicbrainz` sends at most one request a second from the server, whatever the number of callers, holds its turn until the reply is in, follows no redirect and retries nothing on its own.
- **Reported.** The result gives each disc's outcome (`replied`, `not_found`, `kept`, `failed`) and the albums its current reply names: each release group with its title, credit, first year and how many of the reply's releases are of it. `ritornelctl corrections lookup <folder> [--root <name>] | --album <release> [--again]` prints it.

### Replies and facts

- **`lookup_response`** is one reply, verbatim: the catalogue, request kind, key and inclusions, the status (200 or 404), the body and its BLAKE3 hash, and when it came. It is immutable (`lookup_response_no_update`, `lookup_response_no_delete`, and `lookup_response_no_replace` against an `INSERT OR REPLACE`). The newest reply to a request is its current one; a reply the same as the current one is not kept again, and one that differs is kept as the new current one.
- **`evidence_claim`** holds the facts each reply states, per release, read by `reply::read_disc_reply` (`READER_VERSION = 1`): the release's title, status, date, country and barcode; its credit (`album_artist`, `album_artist_join`, `mb_album_artist`); its album (`mb_release_group`, `release_group_title`, `primary_type`, `secondary_type`, `first_release_date`) and the album's own credit (`group_artist`, `group_artist_join`, `mb_group_artist`); how many media it has; and which of them the disc is, with its track count (`disc_number`, `track_count`). Each fact keeps its position, so a join phrase stays with its name. Facts read by another reader version are read again from every kept reply, with no network, when the server starts (`FACTS_METHOD`, `corrections.facts`) and in the next lookup's write (`library_setting` key `corrections.reader_version`); a kept reply the new reader cannot read states nothing.

## Album proposals

A proposal says that one disc of the library is one album: a MusicBrainz release group. It is derived, as plays are, and nothing it says is shown on a wall or written into the library's catalog.

### Working them out

`propose::propose` (`PROPOSER_VERSION = 2`) is a pure function of the disc layouts, the current reply about each disc ID and the files' facts:

- **The subject is one disc:** the files a folder's layouts place, among layouts that are not provisional and have a current reply. A disc whose replies name no release gets no proposal, and nor does a disc with a file that names neither its album nor any artist: a yes would give it the album's title and no credit, and it would show under no artist with songs named for their files, so it waits until its songs and credit can be answered too.
- **Each candidate is an album its replies name,** with its title, the album's own credit, kind, first date, and how many of the replies' releases are of it; the likeliest, with the most releases, first.
- **What a yes would put on the files** (`values`): every file gets `mb_release_group`, and the album's `primary_type` and `original_date` where MusicBrainz knows them. Where other discs of the library are on the same album, each the same single medium of it in every release that holds it and no two the same, the yes joins them: each file gets its disc's `disc_number`, and the files of every disc but the first take the first disc's `album`, `album_artist` and `mb_album_artist` where their own differ. A file with no album title gets the album's. The candidate keeps the files of the first disc it joins its disc onto (`onto`), whose title and credit it takes, so what a yes puts together is known before it is said.
- **What that would change** is worked out cheaply: `moves` when files would join or part, take another album's ID, or share a tile with another disc of the album without joining it; `gains` when a kind or a first year would differ from what the files say; `knows` for an ID alone. The preview says exactly.
- **An ID is computed** from the kind and the anchor, the subject's first-seen file, by its public ID, so a proposal worked out again keeps its ID. Proposals that share their first candidate share a group, named by the proposal whose anchor is the first-seen file among them. A fingerprint is a digest of all of a proposal.

Proposals are worked out again in the same write as anything they rest on: a derivation of the layouts, and a lookup's replies. Only those that differ, by fingerprint, are rewritten (`proposal`, `proposal_item`, `proposal_candidate` with each candidate's `values_json` and `onto_json`, and `proposal_evidence`). A new proposer version is worked out again from stored rows when the server starts (`library_setting` key `corrections.proposer_version`), as are a new reader or layout version.

### Tag values

A value replaces the file's own tag for its field before anything is formed (`values::apply`), for the fields `album`, `album_artist`, `mb_album_artist`, `disc_number`, `mb_release_group`, `primary_type`, `original_date`, `mb_release` and `track_number`, and the item holds that field (`Item::held`); a value of nothing clears the field. The disc rules (`discs::apply`) leave a held album title or disc number as it is. The values answers put on files are read into every load of the library (`apply_in_force` in `load_in`), so the resolver, the projector, dry runs and rebuilds all see them above the files' own tags.

### Showing and previewing

- `corrections.summary` counts the open proposals and their groups, by what their likeliest candidate would change, and says whether lookups are on.
- `corrections.list` lists every proposal by group, with its candidates but without their values. `corrections.get` gives one whole: its files, each disc it rests on with how its layout was found and how many releases the reply names, and each candidate with the values a yes would put on each file.
- `corrections.preview` takes proposals, each with a candidate or its likeliest, and runs the projector twice, read-only (`values::preview`): on the library as it is, and with every chosen value in place. It reports the albums the touched files and everything else on those albums are on now, and after: each one's title, credit, kind, first year, releases, discs and songs. It also counts the songs the values would join into others (`songsJoined`), such as two editions' copies of one song that are two songs now and would be one, and those they would part from the one they are on (`songsParted`); `ritornelctl corrections preview` says both first, as they move what plays and ratings count on.

`ritornelctl corrections list`, `show <proposal>` and `preview <proposal>... [--candidate <release group>]` print them.

## Edition proposals

The discs of an album the library holds two or more of are also proposed as one release of it: an `edition` proposal (`propose::editions`, `PROPOSER_VERSION = 2`), in the album's group, its subject every file of those discs that no answer gave a release. Its candidates are the releases of the album that hold every one of the discs, each at a medium of its own, as the replies about the discs name them, each with the release's own title, date, country and number of media (`proposal_candidate.release_mbid`, `country`, `media`). An album some discs of which are the same medium of every release, such as two copies of one disc, gets none, and nor does an album with one disc or a disc whose layouts place a file at two tracks. A disc an answer already put on a release is one a yes puts these with when it is another medium of the release, and the only release then offered is the one it was said to be; one that is the same medium as a disc of these makes these another copy, put with none of the first copy's discs, so a second copy of an edition is proposed as a release of its own; and one said to be a release that does not hold it is not of this one. Its ID is of its album and its anchor, so two albums proposed for the same discs give two. Several releases holding the discs alike are each a candidate, and the proposal stays open until one is said.

A yes to an edition names its release (`Confirmation.release`) and puts `mb_release` on each file, with its disc's medium as `disc_number` and its place on the disc's layout as `track_number`. It is said with or after the yeses to its discs' album: one whose files are not of that album by a standing yes, or by one given with it, is refused as `invalid`. It rests on those yeses, and for discs already said on the answers that said them (`answer_dependency`), so undoing one undoes the edition too; undoing the edition alone leaves the album's join. What it puts together is the releases of all its discs (`answer_join`). A release ID an answer gave is split by folder where two folders claim one disc and track, as a title is, so two copies of one edition said yes to stay two releases; a release ID the files' own tags give is not, as before.

`ritornelctl corrections confirm <edition> [--release <release>]` and `preview <edition> [--release <release>]` take a release; `list` and `show` say which proposals are editions and each release's title, country, year and discs.

## Answers

An answer is one library write, and the ledger is append-only.

### Saying yes

`corrections.confirm` (command, `full` session) takes proposals, each with a candidate and the fingerprint it was shown. While a scan is running it is refused as `unavailable` (`scan_running`), as an undo and a keep-apart are: a scan between two of its batches has read files it has not yet judged as moved, missing or replaced. The job worker claims no job between that check and the answer's write (`Core::answering`). In one write (`answer_store::confirm`):

1. Layouts a scan left due are worked out first, and with them the proposals, so that a change a scan made since the proposals were shown is seen. Each proposal is then read as it is now. One whose fingerprint differs is refused as `conflict` with the reason `plan_stale`, and nothing is written. A proposal named twice, or answers that give one field of one file different values, are refused as `invalid`.
2. The catalog is worked out again in the same transaction with the values in force and the new ones above them (`resolve_in`), and plays follow their files.
3. A recording, an appearance or a release the write emptied, one no live file is on any more, is redirected to where its file went (`redirect_to_id`, `canonical_id`), so a rating, a queue entry or a correction naming it follows, and so does a play of a scrobble or a Spotify stream bound to it, with the artists and record it was heard as (`history_store::catalog_changed`). A queued song of a bonus disc joined to its album still plays. When any row was redirected, the catalog is worked out again with the redirects, so that edits and plays on those rows follow them in the same write, and so on until no more is emptied (`project`).
4. An `answer` row is kept for each (`verb = 'confirm'`): the proposal and its fingerprint, the candidate, who gave it and through which session, the layout, reader and proposer versions, the evidence it rested on by value (`evidence_json`: the candidate and the others it was chosen among, each disc ID with the reply it was read from and its layouts with the sidecar revisions they were read from, and the values), and, for its undo, where each of its files and every other file the write moved was (`before_json`). The redirects the write set are kept in `answer_redirect`, and what it puts together in `answer_join` (below). The answers of one write each keep the files it moved and its redirects.
5. Its values go in `answer_value`, each with the origin the proposer gave it: `catalogue` for what MusicBrainz said, `library` for a title or credit taken from another disc of the library.
6. The proposals are worked out again: an answered file is in none.

What a yes puts together is worked out before it is projected (`values::join_of`): the releases its own files and the files of the first disc it joins them onto (`proposal_candidate.onto_json`) are on, their groups, and the group of every release that is that album now by its files' own tags, every file of it saying so; a release another answer made that album is not counted, as that answer's own join covers it while it stands. It is kept in `answer_join`, with the album it names (`album_mbid`), less any of those releases the yes left apart, as two whose files' own release IDs differ, or, said with an edition, any its own values would not put on one release, and while the answer stands the projector counts the rows it joins as one, and the groups of every standing yes to one album as one too (`Library::answer_joins`): the guards against collapsing two releases, or two groups, that both carry input of their own let that join through, because a person said yes to it, and stand for any other. A release retagged later to the same title or album ID is not joined by the answer, and once the answer is undone its join counts no more. `corrections.preview` works out the same join for each choice, so what it shows is what a yes does, but for a person's edit on a release the yes empties: the edit follows the release's files once the yes is said, and the preview does not show it.

### Undoing

`corrections.undo` takes answers, each alone or together, in any order. An answer rests on another when it took its album's title or credit from files the other gave them (`answer_dependency`, kept when it is said), and undoing one undoes every standing answer that rests on it, and those resting on them. In one write (`answer_store::undo`), each gets an undo answer (`verb = 'undo'`, `undoes_answer_id`; one undone because it rests on another names it in its evidence), its values are withdrawn (`withdrawn_by_answer_id`, set once, and only by the undo of the answer that wrote them), what it put together counts no more, and the redirects it set are cleared where they still lead where it led them.

Each file is then handed the rows it was on before (`answer_store::handed`): the appearance (`Item::prior`), which it votes for in place of its current one, and the recording (`Item::prior_recording`), which it takes again if the resolver parts it from the one it is on, and for its release the group it was in (`Library::prior_groups`), since a group has no redirect. An answer moved a file when it gave it values, or when the file moved in its write and no answer of that write gave it values. What a file is handed is where it was before the first of a run of answers that moved it, once none that moved it stands; a file an answer still standing moved or gives values to is handed nothing and goes where the values in force put it. The files of an answer undone earlier while one undone now stood are handed theirs again too, as that one may have kept them from it. A redirect an answer still standing or an undo set on a row a file is handed is cleared first, so the file can be on it again; a row still left with no file is led on again, and one an answer led elsewhere whose files are now somewhere else is led to where they went. A redirect a person made by hand is never moved or cleared by an answer. What files are handed is taken or not in the first pass of the projector, and the passes after it, which let edits and plays follow the redirects, keep what it made. So answers given together are undone one at a time, and an earlier one is undone while a later one about the same files stands: where a file goes comes from the values still in force, and what it is handed only decides which existing row, and so which public ID, it is on. Where what it is handed does not fit, as when the row leads on to another, it stays where it is. The projector then gives back the recordings, releases, appearances and groups the files had, under the IDs they had, and plays follow. A row the undo left with no file, and a row the files were on before the undone answers that still has none, as one an answer still standing needs, is led to where most of its files now are; the undo keeps these redirects as its own. A release an answer led on is the answer's and not a merge: the projector does not hold the files of the release it leads to together as it does a merge's (`Library::answer_redirects`). An answer is undone once; an undo is not undone, and a yes is said again by confirming.

`corrections.preview` with `undo` instead of `choices` previews an undo by rehearsing it: the undo runs in a write that is always rolled back (`LibraryStore::rehearse`), so what it shows is what the undo does, and nothing is kept: the albums now and after, the songs it would join or part, each value it would withdraw with what the file says now and would say after, and every answer it would undo (`undoes`), those asked for and those resting on them, oldest first.

### Saying no

`corrections.decline` (command, `full` session) says no to a proposal as it was shown, refused as `conflict` (`plan_stale`) if it has changed: not this candidate (`verb = 'decline'`, by its release group, or for an edition its release), or, with `stopAsking`, ask no more about its files (`verb = 'stop_asking'`). `corrections.keepApart` names two releases, and the files on each now are never put on one release or in one release group with the other's (`verb = 'apart'`); it is refused as `invalid` for two releases of a group chosen for both, which holds them together. Each is an answer, kept in `answer_rule` with its files in `answer_rule_item` (for `apart`, each on its side), and in force while the answer stands (`Library::noes`); it names files, so it holds through a rescan, a re-resolve, a rebuild and a move, and it is undone like any answer, its rule withdrawn by the undo (`withdrawn_by_answer_id`, once).

- **Not this candidate.** The proposer offers a candidate no more while most of a subject's files carry a no to it, so a no still holds for a disc that has gained or lost a file. Others are still offered, and new evidence may bring another.
- **Stop asking.** A file asked no more about is in no proposal of the kind it was asked about (`answer_rule.about`): no edition, after a stop on one, and no album or edition, after a stop on an album, since an edition rests on a yes to its album.
- **Keep apart.** The proposer never joins a disc to one kept apart from it, and never proposes them as one edition. The projector never forms a release that holds files of both sides, splitting one that would, each file going with the first part it is not kept apart from, and never joins two groups that would hold both sides, nor keeps a release in a group chosen for one kept apart from it. No call sets a chosen group yet (`release.chosen_release_group_id`); the one that does must keep a keep-apart from evicting a release that is not of the pair from a group a person chose, which the projector does today when that release shares an album ID with the side kept out. The resolver takes their songs as songs of two albums, which tags alone bind only as `tags_bind_across_albums` lets them, and tells two tracks of one release apart by the releases the projector forms for them. Where the projector had them together, the answer parts them, and the rows they leave lead to where they went.

A decline and a stop move nothing shown; a keep-apart may. `ritornelctl corrections decline <proposal> [--candidate <release group>] [--release <release>]`, `stop <proposal>` and `apart <release> <release>` give them.

### Values in force, and what survives

For a file and a field, the values in force are those of the newest answer that wrote that field and is not withdrawn, so a later answer's values lie over an earlier one's and undoing the later gives the earlier back. Values name source items, so they hold through a rescan, a re-resolve, `rebuild-display` and a moved folder. A file whose audio is replaced at its path is judged the same song or not under its item's held values (`values::hold`), so a corrected file ripped again under its old tags keeps its item and its answer.

### The ledger, and what a write says

`corrections.answers` lists the answers, newest first, a page at a time (`limit`, 50 by default and 500 at most, and `before`, the `next` the last page gave): what each said, the album's title as it was shown, how many files it put values on, and which undo undid it. `corrections.answer` opens one to what it rested on and said, read back from `evidence_json` as it was kept: the album said yes to and those it was chosen among, each disc with when its reply came, each layout of them with how it was found, the values it put on each file, named as the file is now, and for an undo of an answer that rested on others, the answers it was undone with. `ritornelctl corrections confirm <proposal>... [--candidate <release group>] [--fingerprint <f>]` confirms each proposal as it is when it runs or, for one, as the fingerprint `show` printed says; `undo <answer>...` undoes them and names first the answers that rested on them and went with them, `preview --undo <answer>...` shows what an undo would do, `answers [--before <answer>] [--limit <n>]` pages the ledger, and `answer <answer>` opens one.

An answer that moved nothing shown says so (`Write::changes_nothing_shown`), and its commit sends no `library` or `list` event.

## Decisions

- **Evidence moves no wall.** No table here is read by the resolver or the projector, and the writes that change them (`scan.sidecars`, `corrections.layouts`, `library.setSettings`, `corrections.lookup`, `corrections.facts`) send no `library` or `list` event (`changes` in `apps/server/src/dispatch/lists.rs`). A scan that finds only sidecars leaves the catalog untouched.
- **Bytes kept, layouts derived.** Sidecar bytes are durable and immutable, and layouts are a versioned pure function of them and the stored lengths, so a better reader is a new `LAYOUT_VERSION` and no rescan.
- **Lengths from the stored duration.** Sectors are worked out from `duration_ms`, not from a sample count the payload does not carry, because the cut to the millisecond still fixes a whole number of sectors. A wrong layout fails safe: an exact disc lookup finds nothing.
- **Read-only roots.** A sidecar is read and never written, renamed or removed, as audio is.
- **Off until switched on.** Asking a service about a library sends something about it, so a library is never asked about until its own switch says so. Sidecars are read regardless, since nothing leaves the machine.
- **The plugin only fetches.** Replies are read in the domain crate, so the facts are rebuilt from kept replies with no plugin and no network, and a dry run never needs the network.
- **A failure is not a reply.** Only a reply MusicBrainz gave is kept; a failure leaves the disc to be asked again.
- **Proposals hang on files.** A proposal's subject and values name source items, and its ID comes from its anchor file, so a proposal outlives a rescan, a re-resolve and a rebuild of the proposals.
- **An answer is a tag value.** A yes writes the values the files would carry had they been tagged right, and the projector reads them above the files' own, so the library after an answer is what a fresh scan of correctly tagged files would show.
- **What the ledger keeps, it keeps by value.** An answer copies the evidence it rested on and names the immutable reply rows it came from, never a derived row, so it reads the same after the proposals are rebuilt.
- **The undo test is the library, not the database.** Append-only rows an answer made stay, and every row it touched has a new `rev`; what is checked is that everything a file or a redirect leads to is as it was, public IDs included.
- **A preview is the projector.** The preview runs the same pure projector a scan does, on the library with the values in place, so what it shows is what a yes would make.
